# 《三国志：治世与乱世》版本路线与执行边界

## 需求源与变更纪律

项目以 `E:\newsanguo` 下四份交付文档为唯一需求基础：

- 理论企划案：回答游戏定位、核心循环、系统支柱、三国化方向和长期版本规划。
- 完整策划开发需求文档：回答程序要实现的对象、字段、状态、流程、跨系统事件和验收方式。
- 数据母表：回答表结构、字段、枚举、公式、效果和样例数据如何沉淀。
- 需求索引与验收矩阵：回答每个系统文档、里程碑、边界和 QA 用例状态。

执行纪律：

- 玩法、字段、状态机、公式、数据表、验收标准默认严格遵循四份文档。
- 不允许凭空新增正式规则；文档没写清楚的内容必须标记为“缺口/待确认”。
- 文档之间冲突时，不静默选择；必须列出冲突点、影响范围、建议取舍，再由项目负责人确认。
- 如需改动业务设计，必须说明原因、根因、影响、副作用，并同步更新项目说明文档。
- 每个版本计划必须标注对应来源：文档章节、数据母表表名、QA 验收项。

映射规则：

- `hero_英雄.xlsx` 主表字段 `id / name / halfBody` 是英雄资源映射的基础。
- `name` 是文本 key，例如 `hero_name_1001`。
- `lang_多语言.xlsx` 将文本 key 映射为中文名，例如 `hero_name_1001 -> 刘备`。

- 程序资源索引必须以 `halfBody` 字段为权威，不得硬性假设英雄 ID 永远等于图片尾号。
- 本项目只复用半身像视觉资源；源项目技能、传记、君略、官职、势力和数值不得导入本项目正式内容库。

## 版本路线

### Prototype V0.1：核心闭环

目标：

- 实现城市、任命、出阵、行军、粮草、接敌、自动战斗、占领、战后整合、存档读档。
- 使用少量测试数据，不伪装成完整内容库。
- 3D 大地图只做战略表达：城池、路线、部队、势力归属、状态调试。
- UI 以调试面板为主，但结构要为后续正式 UI 预留数据接口。

进入下一阶段前必须满足：

- QA_CORE P0 全部通过。
- 无硬性失败条件。
- 核心状态可重复初始化和存档读档。

### Prototype V0.2：系统深化挂载

目标：

- 挂载政令、效果系统、基础外交、基础 AI。
- 验证扩展系统能读取统一核心状态，不破坏 V0.1 闭环。

暂不做：

- 完整外交 AI。
- 完整都督府 AI。
- 全量技能和政令内容库。

### Prototype V0.3：三国特色规则

目标：

- 挂载汉室正统、士族民心、人物关系、降将忠诚、关隘港口水路。
- 验证这些规则能作为策略压力生效，而不是只显示数值。

暂不做：

- 完整水战模式。
- 大量历史事件链。
- 全武将关系网。

### Content Alpha：内容库与 UI 原型

目标：

- 补齐阶段性城池、武将、技能、政令、剧本初始状态；武将数量可以先围绕已可复用半身像资源收缩。
- 建立内容校验工具，避免字段缺失、重复 ID、非法引用。
- 开始正式 UI 信息架构和视觉风格落地，引入可复用英雄半身像资源池、浏览组件和可校验的 UI 导航规格。

### Beta：正式 UI 与体验整合

目标：

- UI 必须达到正式游戏观感。
- 主界面、大地图、城市、武将、任命、出阵、战报、事件、存档界面都应是完整游戏界面。
- 不再依赖开发调试面板完成主要玩法。
- 英雄半身像、势力信息、城市信息、风险提示、战报反馈进入正式 UI 表达。

### 正式版

目标：

- 完整地图、稳定 AI、正式 UI、美术音频、事件链、平衡性和存档兼容达到发布标准。
- 所有正式内容必须可追溯到四份交付文档、项目变更记录或已确认的后续专项文档。
